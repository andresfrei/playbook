# Decisions of the work delivery-versioning

| ID | Date | Decision | Who decided | Their words |
|----|------|----------|-------------|-------------|
| delivery-versioning-1 | 2026-11-22 | The value of the line "Delivery" in a spec comes from the project's default delivery, defined once in `technology.md`. `define` copies it to the spec and asks only when the project has no default or the work needs another way (for example a worktree for parallel sessions). | Andres Frei | Asked where the value of the line "Delivery" comes from: "Default del proyecto (Recommended)" |
| delivery-versioning-2 | 2026-11-22 | The playbook offers three closed forms of delivery for the project's default and the line "Delivery": one branch and one pull request per work; one branch and one pull request per unit; a worktree of its own for parallel sessions. Any other way is written in the owner's words. | Andres Frei | Asked which forms of delivery the playbook offers as closed options: "Tres formas (Recommended)" |
| delivery-versioning-3 | 2026-11-22 | The versioning policy a project writes in `technology.md` has three closed options for when a tag is made: after the merge of each work that `close` recommends versioning; after several works together, when the owner asks; never (the project has no versions). `close` recommends and the owner decides, as today. The policy also says what carries a version and where it is declared (session-cost-6). | Andres Frei | Asked which closed options exist for when a tag is made: "Tres opciones (Recommended)" |
| delivery-versioning-4 | 2026-11-22 | The spec of the work `delivery-versioning` is accepted, with two units: (1) `define`, `close`, and `release` read and write the Delivery and Versioning lines; (2) the list of what every project must define in `audit-wiki`. Both units merge before one new version. | Andres Frei | Asked whether to accept the spec: "Aceptar (Recommended)" |
