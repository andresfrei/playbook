| dialog-learning-3 | 2026-11-27 | The `header` of every question dialog is the question's type, one of fourteen fixed English words that the rule lists and the agent copies as they are, whatever the reply language: Session (close here and go on in a clean session, or go on to the next step), Accept (a spec, a plan, a unit, a close), Delivery (commit, push, pull request, version, release), Load (split a unit, build in parallel, the order of units), Record (write down a rule, a delegation, a memory, a name), Finding (what to do with a finding of an audit or a review), Remote (another machine, credentials, access), Setup (Claude's permissions, skills, plugins, agents), Product (what the product does), Technical (a technology or a mechanism), Design (the visual part), Scope (what is in and what is out), Problem (an obstacle while building), Clarify (a fact only the owner knows). The question and its options stay in the owner's language. Why fixed words: with free headers the same question came out as "Sesión", "Siguiente", and "Seguir". The fourteen are the types measured on 2026-11-27, so the imported history and the new dialogs share one list. The tool describes the header as a "Very short label displayed as a chip/tag (max 12 chars)"; the longest word has nine. | Andres Frei | Shown the fourteen types with what each asks, and asked how the chip is written: "Inglés, fijo (Recomendado)" |

| dialog-learning-5 | 2026-11-27 | This work covers a session with a person at the terminal. Support for a session driven by another session, such as a bot of playbot, is a work of its own, `driven-mode`, to be defined after this one, and its picture is: playbook knows the mode of each session. With a person, the default, nothing changes. Driven: whoever launches the session sets a variable that says the session is driven and where its questions go; playbook's session-start hook sees it and loads a short block in place of the dialog rules: ask in text with the type first, open no dialog, and hand back what cannot be written outside the project. The mode is per session and not a line of a file, as `Build mode:` is, since the same project is worked by hand one day and by a bot the next. Why a mode: rules for bots would otherwise load in every session, also for an owner who never uses playbot, which is optional (playbot-3); and the documentation read on 2026-11-27 (hooks.md, env-vars.md) names no field or variable that tells a session nobody is at its terminal, so the launcher has to say it, as playbot's bot file already does for its guard with `PLAYBOT_BOT=1`. Found by reading playbot: a bot's settings deny `AskUserQuestion` (playbot-18), so it asks in text through SendMessage (playbot-25), and the playbot session relays to the owner in a dialog of its own; until `driven-mode` is built, the hook of this work sees only that relayed dialog and counts it under playbot's folder. | Andres Frei | Asked to accept the spec, chose "Cambiar algo", and said: "revisa el proyecto playbot... la idea de ese proyecto es un manejador externo de sesiones de claude usando playbook... tienemos que darle soporte". Shown three changes to the rules for every session: "no crees qeu seria quizas mejor saber en que modo traabajar playbook? porque quizas no lo trabaje con playbot". Asked whether the two modes, with the driven one set by a variable of whoever launches the session, was the idea: "si". Asked whether the mode is a work of its own or part of this one: "Work aparte (Recomendado)" |
| dialog-learning-6 | 2026-11-27 | Accept the spec of the work dialog-learning, with the units capture, rules, import, table, and learn, and its six proposals: `audit-learning` keeps its trigger and adds the reading of the answered dialogs, one table by type that counts every project on the machine while the departures it lists are those of the project it runs in; no number decides, and a delegation is proposed for a type only when it is one question asked again and again, the first option was taken almost every time, and git undoes a wrong answer, never for Delivery or Remote; a fact the agent did not have becomes a line for the project's wiki or `CLAUDE.md`, a recommendation that missed more than once a correction of the rule or skill that makes it, and an idea of the owner outside the options is only counted; on its first run `audit-learning` imports the history and has the lines with a header outside the list classified before the table; the lines stay on the owner's machine and the plugin's README says that uninstalling deletes them; the hook stores its input as it arrives and parses nothing. | Andres Frei | Asked, with the driven mode moved to a work of its own, whether to accept the spec with its five units and six proposals: "Acepto (Recomendado)" |
