# Spec of the work one-audit

Status: Accepted (one-audit-10).

Delivery: one branch and one pull request per work (delivery-versioning-2).

## What and why (one-audit-1, one-audit-2)

One skill, `audit`, replaces `audit-wiki` and `audit-tools`. It checks everything that sets up Claude in a project: the wiki, `CLAUDE.md` and `CLAUDE.local.md`, the rules, the auto memory, the skills, the agents, the hooks, and the MCP servers. For each piece it asks two questions: does it collide with the playbook or with another piece, and what does it cost in context by Claude Code's documentation.

In huellitas-id on 2026-11-23, about 73KB loaded before the first message: a `CLAUDE.local.md` of 44KB generated by a tool whose source no longer existed and negated by the project's `CLAUDE.md`, a rules file of 10KB with no `paths:`, a `MEMORY.md` with 59 lines and four lines that said "read first", and a wiki README over the hook's budget. The limits of the documentation alone would have caught one of the four.

Claude Code's documentation, read on 2026-11-23:

- context-window.md: "Before you type anything: CLAUDE.md, auto memory, MCP tool names, and skill descriptions all load into context." And: "run `/context` for a live breakdown by category with optimization suggestions."
- memory.md: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence."
- memory.md: "CLAUDE.md and CLAUDE.local.md files in the directory hierarchy above the working directory are loaded at launch." Imports "don't reduce its context cost, because imported files load together with the CLAUDE.md that imports them."
- memory.md: auto memory loads "up to the first 200 lines or 25KB of `MEMORY.md`".
- memory.md: "A path-scoped rule loads when Claude uses the Read, Write, or Edit tool on a matching file."
- costs.md: "Skills load on-demand only when invoked, so moving specialized instructions into skills keeps your base context smaller." And: "Run `/mcp` to see configured servers and disable any you're not actively using."
- costs.md, "Delegate verbose operations to subagents": "Delegate these to subagents so the verbose output stays in the subagent's context while only a summary returns to your main conversation." (one-audit-6)
- hooks.md: the output of a SessionStart hook is capped at 10,000 characters (audit-2026-11-22-1).

Checked live on 2026-11-23: a rule with `paths:` loads in a custom subagent that reads or edits a matching file, and does not load for a file that does not match. In a project under `/tmp`, no project rule loaded at all, so the live check runs in a throwaway repository under the home folder.

## What changes

1. A script of the plugin, `startup-context.sh`, prints the table of what loads at startup for the project it runs in (one-audit-4). One row per source: the path, the level (project, user, or plugin), when it loads (startup or on demand), lines, bytes, and the limit of the documentation it passes, if any (one-audit-3). The sources:
   - each `CLAUDE.md` and `CLAUDE.local.md` from the project's root up to the home folder, `.claude/CLAUDE.md`, `~/.claude/CLAUDE.md`, and each file they import with `@`; limit: 200 lines per file;
   - each file of `.claude/rules/` and `~/.claude/rules/`, and of their subfolders when memory.md says they are read: with no `paths:` it loads at startup, with `paths:` on demand;
   - the project's `MEMORY.md`, in the folder Claude Code keeps for the project under `~/.claude/projects/`, or in `autoMemoryDirectory` when set; the builder checks the folder's naming against the folders that exist. Limit: 200 lines or 25KB, past which it is cut. The memory belongs to the project's level;
   - `docs/playbook/README.md` with the playbook's `rules.md`, against the hook's budget;
   - the active output style, from the settings, the project's before the user's;
   - the descriptions of the skills and agents of the project, of the user, and of the enabled plugins, the playbook included, as a count and a total of characters; a skill with `disable-model-invocation: true` adds no description and is not counted (basics-26).
   The script does not read the MCP servers: the explorer of the tools lists them with `claude mcp list`, and their cost is seen with `/context`. U1 does not change the plugin's README, which U2 rewrites.
2. The skill `audit` joins `audit-wiki`, its `first-run.md`, and `audit-tools`, with their steps and rules; the two old skills are removed, and every mention outside `docs/playbook/works/` moves to `audit` in the same commit: the hook `adopt.sh` and its tests, `close`, `define`, the plugin's README, the repository's README, `docs/playbook/README.md`, `product.md`, and `skills.md` (one-audit-2). Two rules of the old skills change by later decisions: "never for the whole machine" of `audit-tools` gives way to one-audit-5, and "Change nothing there" of `first-run.md` for the auto memory gives way to one-audit-1: the project's memory changes on the owner's yes. `/playbook:audit wiki`, `setup`, or `tools` runs one part (one-audit-9).
3. `audit` explores first and proposes after (one-audit-6). The explorers run on a new agent of the plugin, `auditor`, with Read, Glob, Grep, and Bash and `omitClaudeMd: true` (one-audit-8). With no argument, three explorers run in one message: the wiki against the code, as `audit-wiki` did; the setup and its context cost; and the tools, the plugins and the MCP servers with them, as `audit-tools` did. A finding between two sources comes back with both quotes and their file and line; a finding of one source, such as a limit passed, a definition missing, or a server that does not connect, with its quote and the number or the limit. When the explorers have ended, the main session crosses the findings, removes duplicates, shows every finding in one table, or says why one is dropped, and only then asks the owner, one question at a time. When an explorer fails, the table says so, shows the others' findings, and offers to run that part again. After the answers, the main session makes the light fixes, such as a broken link, writes the line "Last audit", and runs the check again. The first run, which adopts a project and writes files, stays in the main session before the explorers. The explorer of the setup runs the script and, for each piece:
   - a collision between pieces is reported as the other collisions, with both quotes: an instruction that another file negates, a generated file whose source no longer exists, two memory lines that each say they are read first;
   - content that applies only sometimes gets a proposal of the documentation's way to load it on demand: a skill, `paths:` in a rule, a `CLAUDE.md` in a subfolder, or a memory topic file (one-audit-3);
   - what belongs to the project changes on the owner's yes; what belongs to the user's level only when the owner asks for it explicitly (one-audit-5).
   The audit closes by telling the owner to run `/context` for the real numbers.

## Out of scope

- Running `/context`, `/mcp`, or `/memory`: built-in commands are the owner's to type.
- A threshold of the playbook's own (one-audit-3).
- Measuring the system prompt and Claude Code's own tools: the project cannot change them.
- `claudeMdExcludes` and the managed policy `CLAUDE.md`: shown when present, not reasoned about.
- `audit-learning`, which stays a skill of its own (one-audit-2).

Its setup has a `CLAUDE.local.md` over 200 lines with an instruction that `CLAUDE.md` negates and a first line that says it is generated from a file that does not exist, a rule with no `paths:`, a `MEMORY.md` with two lines that say "read first", and a wiki README over the budget. `/playbook:audit` runs the three explorers in one message; after all three have ended it shows the four sources and the two collisions in one table, proposes a way out for each, changes nothing before the owner's answer, and leaves every row of the user's level unchanged. `/playbook:audit setup` runs one explorer. A repository with no wiki is adopted, as on the first run before.
